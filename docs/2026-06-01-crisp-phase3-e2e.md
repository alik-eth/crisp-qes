Final acceptance gate for the CRISP-QES fork. This records the headline result

## P1 — THE GATE: on-chain acceptance of a REAL proof ✅ PASSED

This is the on-chain analog of the Task 5 SDK self-verify gate. We deploy the
**REAL** regenerated QES Honk verifier (`HonkVerifier` from
`contracts/CRISPQESVerifier.sol`, `NUMBER_OF_PUBLIC_INPUTS = 24`, built with the
bundled bb 3.x that matches the bb.js runtime) behind `CRISPQESProgram`, with a
`MockEnclave` supplying the E3 state (no ciphernodes). We then drive a REAL fold
proof (generated by the crisp-sdk QES path) through `publishInput` and assert the
on-chain `honkVerifier.verify` passes.

### Fold public-input layout (8 elements, confirmed)
```
[0] prev_ct_commitment   (0 for a first vote)
[1] enrollment_root      (census root)
[2] nullifier            (per-petition slot key)
[3] is_first_vote        (1 for first vote, 0 for mask/update)
[4] num_options          (3)
[5] final_ct_commitment  -> on-chain encryptedVoteCommitment
[6] petition_id          (42 for the real vote; 0 on the mask path)
[7] pk_commitment        (fold return value == E3.committeePublicKey)
```
The 16 pairing-point fields the EVM verifier needs are inside the proof bytes
(`p.pairingPointObject`), NOT in `publicInputs`; the verifier requires
`publicInputs.length == 24 - PAIRING_POINTS_SIZE == 8`, which is exactly what the
contract builds.

### Pub-array vs proof-publics issue found AND resolved (mask path)
The first mask run reverted `SumcheckFailed()`. Element-by-element diff of the
contract's `pub[8]` vs the mask proof's publics found the mismatch at **pub[1]
(enrollment_root)**:

- The leaf circuit (`crisp_qes`) does NOT constrain `enrollment_root` on the mask
  path — the `assert(recomputed_root == enrollment_root)` is gated behind
  `is_mask_vote == false`. The SDK mask path therefore passed `enrollmentRoot = 0`.
- But `CRISPQESProgram.publishInput` ALWAYS sets `pub[1] = e3Data[e3Id].enrollmentRoot`
  (the round's census root) for EVERY input — real OR mask.
- So the mask proof's pub[1] (0) ≠ the contract's pub[1] (the nonzero round root)
  → on-chain sumcheck failed.

**Resolution (no circuit/verifier/contract-logic change):** a mask proof must
carry the round's census root as its (in-circuit unconstrained) `enrollment_root`
public input. This is sound because the circuit ignores it when masking; it is
purely a public-input alignment requirement. Fixed in:
- the fixture generator (mask now uses the real `enrollmentRoot`), and
- the production daemon (`services/mask-daemon`): `buildMaskProofInputs` now
  REQUIRES `enrollmentRoot`, threaded through `MaskDaemon.sweepRound` via a new
  `SlotSource.getEnrollmentRoot(e3Id)` (HTTP `POST /qes/enrollment-root`).

After binding the root, all 4 on-chain tests pass.

The other pub fields lined up on the first try: pub[0] prev_ct (storage == real
final_ct), pub[2] nullifier, pub[3] is_first_vote (`prevCommitment==0?1:0` == 0 for
the mask), pub[4] num_options, pub[5] commitment, pub[6] petition_id (0 in the mask
tuple, matching the mask proof), pub[7] pk_commitment.

## P2 — voter submit encoding fixed in the SDK ✅

`packages/crisp-sdk/src/vote.ts` `encodeSolidityProof` was still the pre-QES
address-keyed tuple `(bytes, address, bytes32, bytes)`. It now emits the QES tuple,
byte-identical to the daemon's `services/mask-daemon/src/maskInput.ts`
`encodeQesPublishInput` and to what `CRISPQESProgram.publishInput` decodes:

```
(bytes noirProof, bytes32 nullifier, uint256 petitionId, bool isMask,
 bytes32 encryptedVoteCommitment, bytes encryptedVote)
```

Field sources are the fold proof's public inputs: nullifier = pub[2],
encryptedVoteCommitment = pub[5], petitionId = pub[6] — identical index reads in
both the SDK and the daemon. `encodeSolidityProof(proof, isMask=false)` defaults to
a real vote; a `encodeMaskSolidityProof` convenience wrapper (= `encodeSolidityProof(proof, true)`)
was added and exported. The QES submit fields (`nullifier`, `petitionId`, `isMask`)
were threaded into the high-level `VoteProofInputs` / `MaskVoteProofInputs` /
request types.

This is exactly the encoding the P1 on-chain test feeds to the accepted verifier,
so P2 is validated transitively by the gate.

## P3 — live fake-zkVM stack E2E ⏸️ NOT BROUGHT UP (time-boxed; documented)

Per the task ("high environment friction… TIME-BOX it; P1 is the real gate"), the
full live stack was NOT brought up. Concrete blockers (all pre-QES per Task 6):

- **Deploy script** (`deploy/deploy.ts` + `deploy/crisp.ts`) deploys `CRISPProgram`
  + the `CRISPVerifier.sol` HonkVerifier and registers config key `e3_program ->
  CRISPProgram`. Adapting to `CRISPQESProgram` + `CRISPQESVerifier.sol` is a
  localized factory swap (single file, `crisp.ts`) — feasible — but it also needs
  the full Enclave protocol deployed (CiphernodeRegistry / BondingRegistry /
  SlashingManager) plus a running ciphernode committee.
- **Coordination/program servers are Rust** (`server/`, Actix). The vote-broadcast
  route (`server/src/server/routes/voting.rs`) is address-keyed pre-QES; it does
  NOT speak the nullifier-keyed QES `publishInput` tuple, and there is no
  `/qes/active-slots` or `/qes/enrollment-root` route (the daemon's `HttpSlotSource`
  expects both). Adding QES-aware Rust routes + a fake-zkVM tally driver for the
  QES plaintext layout is multi-hour work.
- The daemon therefore submits **on-chain directly** via `OnChainSubmitter`
  (`publishInput`) rather than through a server relay — which is exactly the path
  the P1 test exercises against the real verifier.

What the on-chain test DOES cover of the E2E intent, on a real EVM (Hardhat EDR
deploys real bytecode): real vote accepted by the real verifier → slot created →
mask accepted on the slot → `decodeTally` over a numOptions=3 plaintext. The only
unexercised pieces are the Rust ciphernode decryption and the Rust server relay;
the cryptographic + contract acceptance gate (the point of Phase 3) is fully closed.
