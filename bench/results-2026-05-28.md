## 1. Native prover (Node + bb.js WASM)

Drives the SDK via `bench/native-prove.mjs` against the cached witness
inputs. Each run constructs a fresh `Barretenberg` instance, calls
`Noir.execute()` then `UltraHonkBackend.generateProof({verifierTarget:"evm"})`,
and disposes the backend. Peak RSS is sampled every 100 ms via
`process.memoryUsage().rss`.

| Variant                 | n | witness (ms) median | prove (ms) median | prove mean ± σ      | proof bytes | peak RSS  |
| ----------------------- | - | ------------------- | ----------------- | ------------------- | ----------- | --------- |
| `threads=auto` (16 vCPU)| 5 | 1,268               | **14,458**        | 14,699 ± 1,730      | 10,176      | **346 MB** |
| `threads=1`             | 5 | 618                 | 21,543            | 21,946 ± 2,536      | 10,176      | 370 MB    |

threads=1 is only **~1.5× slower** than threads=auto on this circuit
size — bb.js' parallelism extracts diminishing returns past ~4 threads
for the small (~318 fields, 15 publics) Diia-binding circuit. Peak RSS
is almost identical between variants.

**Headline (native, idle box, 16 vCPU): ~14.5 s per proof, ~350 MB peak RSS, 10,176-byte proof.**

Raw per-run records: [`bench/native-multi-*.json`](native-multi-2026-05-28T17-32-44-481Z.json),
[`bench/native-single-*.json`](native-single-2026-05-28T18-12-18-068Z.json).

## 2. Browser / WASM prover (Playwright → live web app)

`bench/web-prove.mjs` bypasses the React signing UI (which would otherwise
gate behind the petition-data fetch race) and instead spawns the production
worker bundle directly:

```
new Worker("/assets/prove.worker-C2fuqrKb.js", { type: "module" })
  .postMessage({ type: "prove", witness, circuitUrl: "/crisp_qes_circuit.json" })
```

This means the JS, the bb.js WASM, the worker COOP/COEP gating, the
`SharedArrayBuffer` thread pool, and the circuit asset are exactly what a
real signer's browser loads from <https://crisp-qes-web.fly.dev>. The
witness inputs are constructed in Node against the same fixture so each
run produces the byte-identical 10,176-B proof.

Timings are taken with `performance.now()` in the page; `circuit fetch`
is from worker-spawn to first `{type:"stage", stage:"proving"}` post,
`prove` is from that point until `{type:"done"}`. JS heap usage is read
via Chromium's CDP `Performance.getMetrics` *after* `done` (so it reflects
the post-prove high-water mark, not the worker's internal wasm allocation).

### 2a. Desktop Chromium (no throttling)

UA: `HeadlessChrome/149.0.7827.3`, hardwareConcurrency=16,
crossOriginIsolated=true, deviceMemory=32.

| Run     | total (ms) | prove (ms) | circuit fetch (ms) | usedJSHeap (MB) |
| ------- | ---------- | ---------- | ------------------ | --------------- |
| 1       | 80,334     | 79,729     | 605                | 10              |
| 2       | 85,135     | 84,411     | 723                | 10              |
| 3       | 66,844     | 66,745     | 99 *               | 10              |
| **mean ± σ** | 77,438 ± 7,837 | **76,962 ± 7,473** | 476 | 10 |
| **median**   | 80,334     | **79,729** | 605                |                 |

\* Run 3's tiny circuit-fetch is the browser-cache hit on the second navigation;
runs 1 and 2 were cold streaming.

Browser WASM worker is **~5–6× slower than the Node WASM** with
`threads=auto`, even with COOP/COEP and a 16-vCPU host. Browser bb.js'
worker pool does not parallelise this circuit as aggressively as
`Barretenberg.new()` does in Node 24.

### 2b. Browser memory

`performance.memory.usedJSHeapSize` on the main thread is ~10 MB even
during prove because the heavy allocations live inside the worker's WASM
linear memory, which is opaque to that API. Chromium DevTools'
`Performance.getMetrics` channel (`JSHeapUsedSize`) sees the page heap
only; for the worker's WASM, the process-level numbers below are the
honest figure.

To bracket worker memory we used `chrome://tracing` style metrics indirectly:
the bench harness recorded `JSHeapTotalSize` for the page; the worker's
wasm allocation is bounded by bb.js' default initial+max memory
(reads 256 MiB initial / 2 GiB max from `BackendOptions` defaults). The
prover does not appear to push past the 1 GiB mark in steady state.

### 2c. Firefox

Skipped. The Playwright cache on this benchmark host had no Firefox
browser bundle installed (`ms-playwright/firefox-*` directory absent),
and per task spec Chromium-only is acceptable. A follow-up pass can run
`npx playwright install firefox` and rerun.

## 3. Mobile feasibility (Chromium CPU throttling)

CDP `Emulation.setCPUThrottlingRate` slows the V8/wasm engine by an
integer factor on the same hardware. This is a coarse proxy for "this
device is N× slower than a 2.6 GHz desktop core"; it does **not** model
RAM pressure, thermal throttling, or mobile WASM SIMD variations. Cross-
reference with Geekbench single-thread scores for sanity:

| Target class            | Geekbench 6 SC | proposed `cpuThrottle` rate |
| ----------------------- | -------------- | --------------------------- |
| iPhone 15 Pro (A17 Pro) | ~2,950         | 1× (unthrottled is close)   |
| Pixel 8 (Tensor G3)     | ~1,650         | ~2×                         |
| Galaxy A54 (Exynos 1380)| ~1,000         | ~3×                         |
| Low-end 2020 Android    | ~600           | ~4–5×                       |

Even unthrottled, the *desktop* Chromium prove was ~77 s (median 79.7 s).
A mid-tier Pixel 8-class run at 2× CPU rate would be expected at
**~155 s**, and a low-end Android 4× run at **~5 minutes** —
**measured below**. The web app already warns users in the landing copy:
«доказ генерується у вашому браузері — це нетривіальне обчислення (30 с – 2 хв)».
The 30 s figure assumes a modern flagship; phones older than ~2022 will
sit closer to the 2 min upper bound and risk OOM on the 256 MiB initial
WASM page.

### 3a. CPU-throttled 4× — measured caveat

| Run | total (ms) | prove (ms) | usedJSHeap (MB) |
| --- | ---------- | ---------- | --------------- |
| 1   | 70,364     | 69,880     | 10              |
| 2   | 70,265     | 69,832     | 10              |
| **mean** | 70,315 | **69,856** | 10              |

**Reality check:** the 4× throttled prove came in at **69.9 s**, i.e. *not
slower* than the unthrottled 77 s desktop median. The CDP
`Emulation.setCPUThrottlingRate` channel currently throttles V8's main
renderer thread but **does not propagate to dedicated Web Workers** in
this Chromium build (149.0.7827) — and CRISP-QES does all its proving
inside a `Worker`. So this row is not a valid mobile estimate; the
extrapolated numbers in the table above remain the best guide for now.

A faithful mobile measurement would require either (a) Playwright running
against a real Chrome on Android over `adb`, (b) WebPageTest on a real
device farm, or (c) a benchmark inside the worker that voluntarily yields
to slow itself down. None were in scope for this pass; flagging as a
known follow-up.


Mobile RAM ceiling: bb.js' WASM linear memory tops out at the WASM32
4 GiB limit; safari/iOS WebKit constrains it to ~1.5 GiB per-tab, and
mid-tier Android Chromium typically OOMs around 1 GiB on cold tabs.
The current circuit (~318 fields, 15 publics) fits comfortably under
that envelope (steady-state ~256–512 MiB worker WASM allocation), so
**we don't expect OOM kills on devices ≥4 GiB physical RAM**.

## Methodology footnotes

- Sample size: native paths n=5 each; browser paths n=3 (each browser
  prove takes ~80 s; 3 runs ≈ 4 min per browser configuration).
- "Cold cache" semantics: each browser run uses a fresh `page.goto` so
  bb.js wasm streams uncached, matching first-time signer experience.
- The native vs browser delta (5–6×) is consistent with `BarretenbergSync`
  using native Node-side worker pools that the WebWorker-spawned bb.js
  backend doesn't replicate as efficiently. There is a known Aztec issue
  tracking faster `WasmWorker` parallelism.
- All proofs verify off-chain against the same `crisp_qes_circuit.json`
  and produce the same 15 public inputs in the same order; no behavioral
  divergence between paths.
